# ADR-0016: Measured tweaks — measure first, derive the value, keep the measurement with the backup

- **Status:** Accepted
- **Date:** 2026-10-07
- **Related:** [ADR-0015](0015-tweak-value-from-measurement.md) (a value measured inside `apply()`, DNS), [ADR-0003](0003-tweak-framework.md) (backup/restore), [ADR-0004](0004-watchdog-safety.md) (watchdog), [ADR-0005](0005-unelevated-server-uac-writes.md) (UAC writes), [ADR-0007](0007-measured-impact.md) (before/after evidence), [ADR-0008](0008-failover.md) (failover)

## Context

Every tweak so far writes a fixed value (`Disabled`, `0`, `30`). The next group — an upload limit against bufferbloat, an MTU from path-MTU discovery, the fastest DNS server — needs a value **computed from a measurement of the network in use**. The hand-tuned session of 2026-08-31 shows both the benefit and the trap: a `NetQosPolicy` throttle at 15 Mbps cut the worst latency under upload from 1880 to 403 ms, but 15 Mbps was typed by hand for one line and one plan; on a faster plan it wastes bandwidth, on another network it means nothing. ADR-0003 has no notion of "where did this value come from" or "is it still right".

[ADR-0015](0015-tweak-value-from-measurement.md) settled this for `dns_fastest`: the benchmark runs inside `apply()`, in the elevated process, and "on" is read from the configuration. That shape does not fit a measurement that loads the line: it loads the line for ~10 s (about 125 MB per 100 Mbps of upload), takes ~15 s in all, must happen while the tweak is off, decides whether there is anything to fix at all (and so whether a UAC prompt should be shown), and has to be repeated afterwards to prove the effect. This ADR covers that second kind of measured tweak; a cheap measurement whose result only picks among fixed values keeps the ADR-0015 shape.

## Decision

1. **A measured tweak** is a tweak whose target value is a pure function `derive(measurement) -> value` of a measurement taken on the current network just before enabling it. The catalog declares the measurement kind, the safety margin and the bounds; backup, verification, rollback and restore stay exactly as in ADR-0003 (restoring never needs the measurement).
2. **Who measures.** The measurement generates real traffic, so it runs only on an explicit user action (the switch in the UI, `enable --apply` on the command line), unelevated, in the caller (server job or CLI) — never in the monitor and never on a timer. It must be taken **while the tweak is off**: measuring through the tool's own limit would measure the limit and ratchet it down on every re-calibration.
3. **The elevated helper does not take a value, it takes the measurement.** `app.elevated tweak-enable <id> --measurement <base64 JSON>` re-validates the measurement (shape, ranges, taken at most 10 minutes ago) and derives the value itself with the same function. A forged measurement can at worst produce a value inside the declared bounds.
4. **The measurement is stored with the backup**, under `measurement` in the tweak's `backup.json` entry next to `original`: the measured values, `measured_at`, `network` and the derived `value`. `network` is the first 16 hex digits of SHA-256 over the default gateway's IPv4 and MAC address, so the router is recognised without the file holding the SSID, the MAC or the IP address. The field is rewritten on every successful enable; `original` keeps the "never overwrite" rule of ADR-0003.
5. **Safety margins and refusals** are part of `derive` and are tested as pure functions. For the upload limit: cap = 85% of the measured upload, rounded down to 0.1 Mbps, never below 1 Mbps nor above 1000 Mbps. `derive` refuses — and nothing is written, no UAC prompt is shown — when the measurement is unusable (load below 1 Mbps, fewer than 8 latency samples attempted — a ping lost under load is a symptom, not a missing sample, and counts as the ping timeout), when it reached its own ceiling (a load phase stops at a fixed volume, `MAX_BYTES`, so it cannot report more than that volume over the phase: from 95% of that ceiling on, the line may be faster and the cap would be wrong — added 2026-10-07), when there is nothing to fix (latency under upload rises less than 30 ms over idle, the diagnostics "ok" threshold), or when the result falls outside the bounds.
6. **A changed network never triggers a write.** The applied value stays when the network changes. The UI marks the tweak *measured on another network* when the current network id differs from the stored one, and *measurement is old* after 30 days, and offers to measure again. Re-calibrating is the user turning the tweak off and on again — each step a click (and a UAC prompt when not elevated). So writes are bounded by user clicks, and no loop between the monitor and a tweak can exist. This is safe for the upload limit because a wrong value cannot disconnect anyone: a cap above the new line's speed has no effect, and a cap below it only limits the upload speed.
7. **Proof right after applying** (a short form of ADR-0007): the server or CLI repeats the same measurement immediately after enabling and records a `tweak_verified` event with the latency rise before and after. The tweak *helped* when the rise dropped by at least 30% and by at least 20 ms; otherwise the result says it did not help and suggests turning it off. It is never turned off automatically: one noisy measurement must not undo the user's choice. The 24-hour comparison of ADR-0007 still applies as for any tweak.
8. **Watchdog and failover.** A measured tweak that does not restart the adapter (the upload limit) is not `disrupts_network`; it still sets the "recently changed" time the watchdog uses for its grace period (ADR-0004). The upload limit applies to all outbound traffic of the PC, whatever the interface (a `NetQosPolicy` has no condition that follows an adapter across DHCP changes): when failover moves traffic to a backup path (ADR-0008), the limit still applies, and the network id tells the UI that the value was measured elsewhere. Failover and the watchdog never change a measured tweak.
9. **What the UI shows**: next to the switch, where the value comes from ("Limited to 34.0 Mbps — 85% of the 40.0 Mbps upload measured on 2026-10-07"), the stale-network/old-measurement flags, and for the upload limit that the download direction can only be shaped on the router (SQM).

## Consequences

- ✅ The value follows the line it was measured on; the user sees the measurement behind it and the evidence after it.
- ✅ The helper with Administrator rights still trusts nothing from its caller; the pure `derive` functions carry the safety margins and are tested without a network.
- ✅ Restore is unchanged: turning a measured tweak off needs neither a measurement nor the network it was measured on.
- ⚠️ Enabling takes longer (two measurements of ~15 s each around the UAC prompt) and moves real data (about 125 MB per 100 Mbps of upload, per measurement).
- ⚠️ Moving to another network does not adjust the value by itself; the user has to re-calibrate when the UI asks.
- ⚠️ The verification right after applying is a single measurement; it can be noisy. That is why it only advises.
