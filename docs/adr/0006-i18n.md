# ADR-0006: Internationalization — JSON catalogs, English by default, store messages rather than text

- **Status:** Accepted — supersedes decision Q9 ("Vietnamese UI") in [OPEN-QUESTIONS.md](../OPEN-QUESTIONS.md)
- **Date:** 2026-10-04

## Context

The user asked for a selectable language, **English by default**, with other common languages added afterwards — before the UI mockup is made (SIC-27). Currently, display strings are hard-coded in the code (mostly in Vietnamese), and there are two places that **store translated text in the DB**: diagnostic results (`diagnostic_runs`) and the log (`events`). Once text is stored, its language can no longer be changed. Constraints: standard library (ADR-0001), the UI runs offline.

## Decision

1. **One JSON catalog file per language** `app/locales/<BCP 47 code>.json` (`en.json`, `vi.json`, later `zh-Hans.json`…). Flat namespaced keys (`notify.outage.router.title`, `ui.nav.overview`…). Adding a language = adding a file; no code changes.
2. **English is the canonical and fallback language.** A key missing in the selected language ⇒ use English; missing in English as well ⇒ show the key itself (and log it once) — never fail.
3. **Language selection:** `settings.json` → `ui.language`, default `"en"`; `"auto"` = follow the Windows display language, matching the full code first and then the base language (`pt-BR` → `pt`), falling back to English if nothing matches. Changed via `POST /api/settings {"ui": {"language": "vi"}}`, taking effect immediately in the running process.
4. **Store messages, not text.** Backend-generated content that is viewed again later (diagnostic results, log events) is stored as `{"key": ..., "params": {...}}` and **translated at display time** according to the selected language. A parameter can nest another message. Old records that are plain text are displayed verbatim. Content used only immediately (toasts) is translated at send time.
5. **Safe formatting:** only `{name}` or `{name:format}` is accepted; no attribute/index access (`{x.__class__}` is ignored) — translations are data and must never become code. Decimal numbers use a comma for languages that use a decimal comma (vi, fr, de, es, pt…).
6. **Plurals:** a catalog value can be `{"one": "...", "other": "..."}`, chosen by the `count` parameter and a minimal rule per language (en/de/es/it/pt: `one` when 1; fr: `one` when 0–1; vi/zh/ja/ko: always `other`).
7. **The UI** fetches the entire catalog for the selected language (already merged with the English fallback) via `GET /api/i18n`; no text is hard-coded in HTML/JS.
8. Source code (variable names, comments) stays in English; ~~documentation in `docs/` stays in Vietnamese~~. **Amended 2026-10-04:** the repository became public, so all documentation (README, CHANGELOG, `docs/`, ADRs, CLAUDE.md) is written in English; only the UI catalogs in `app/locales` are translated (`tests/test_docs_language.py` enforces it).

## Consequences

- ✅ Changing the language also changes old diagnostic results and old log entries (from when the migration is complete).
- ✅ Tests check automatically: every key used in code exists in `en.json`; translations have no extra keys and no missing/extra placeholders compared with English.
- ⚠️ Moving the ~300 existing string lines into catalogs is a large job, done module by module (SIC-41, SIC-42); during the migration the UI will mix two languages.
- ⚠️ Disconnect reasons taken from the Windows log (`Reason: ...`) are Windows' own text and are kept verbatim.
